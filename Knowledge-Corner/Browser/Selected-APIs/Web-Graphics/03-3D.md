# Web Graphics Today — Chapter 3: 3D

*Part of the series "Canvas, SVG, 3D — from the browser's point of view." Status: August 2026.*

---

Chapters 1 and 2 were about two mature technologies arguing over a settled question: bitmap or DOM. This chapter is about a technology stack in the middle of an actual changing of the guard, live, this year, with a genuine casualty list. If you want the chapter where "deprecated" stops being a footnote and starts being the plot, you found it.

Three layers claim the word "3D" on the web, and they are not a hierarchy — they solve different problems and you'll likely use more than one on the same page.

---

## 1. The Cheap One: CSS 3D Transforms

Before any GPU pipeline gets involved, the browser already has a 3D trick up its sleeve: `transform-style: preserve-3d`, `perspective`, `rotateX/Y/Z`, `backface-visibility`. This isn't a 3D scene with geometry and lighting — it's a 4×4 matrix applied to a flat, 2D layer, handled entirely on the compositor thread.

```css
.card {
  transform-style: preserve-3d;
  transition: transform 0.6s;
}
.card:hover {
  transform: rotateY(180deg);
}
```

That's a card flip, a parallax hero section, a rotating product thumbnail — and it's essentially free, because the compositor is already doing layer transforms for scrolling and animation anyway; tilting a layer in a third dimension costs almost nothing extra. The moment you need actual geometry — a mesh, a light source, a camera that moves through a scene rather than a flat plane that rotates in place — you've outgrown this layer and you need one of the next two.

---

## 2. WebGL: The Twenty-Year Workhorse, Now Being Quietly Retired From the Front Row

WebGL wraps OpenGL ES for the browser: you allocate buffers, compile GLSL ES shaders, bind them into a pipeline, and issue draw calls, all through an API that's deliberately close to the native mobile-GPU standard it's based on. Under the hood, browsers don't actually run OpenGL — Chrome and Firefox both translate WebGL calls through ANGLE into Direct3D on Windows, Metal on macOS, or Vulkan on Linux, because native OpenGL drivers on Windows in particular have been a security and stability liability for a decade. You've been running a translation layer this whole time without necessarily knowing it.

**WebGL 2 is universal now** — every major engine ships it by default, Internet Explorer being the one hard exclusion (and if that's still a target, you have bigger problems than this document can solve). Practically speaking, feature-detecting WebGL 1 vs. 2 in 2026 is a formality, not a real branch in your code.

**Here's the deprecation with actual teeth:** Chrome has been removing automatic fallback to **SwiftShader** — the software (CPU-based) WebGL renderer that used to quietly kick in on machines without a usable GPU. The reasoning is blunt and, frankly, correct: SwiftShader runs JIT-compiled code inside the GPU process, which is a real attack surface, and silently downgrading a user from hardware-accelerated rendering to a CPU emulation they never asked for and can't see happening is a bad experience nobody could debug. Since Chrome 130, WebGL context creation on GPU-less systems **fails outright** instead of silently degrading. If your code assumes `getContext('webgl')` always returns something, that assumption is no longer safe — you need to handle a `null` return and either fall back to Canvas 2D (Chapter 1) or tell the user plainly that their device can't run this.

WebGL isn't dead, isn't dying next quarter, and will be the pragmatic choice for years on older hardware and constrained platforms. But it has stopped being where the platform's forward momentum lives. That's the next section.

---

## 3. WebGPU: The Actual Successor, and It Just Finished Shipping Everywhere

WebGPU isn't "WebGL but newer" — it's a different generation of API built on the same modern foundations game engines have used for a decade: Direct3D 12, Metal, Vulkan. Instead of WebGL's immediate-mode "bind this, draw that" model, WebGPU works in explicit **command buffers** and **pipeline objects** you build up front and submit in batches — closer to how the GPU actually likes to be talked to, which is a large part of why it performs better under real workloads. It ships its own shading language, **WGSL**, rather than reusing GLSL.

The genuinely new capability, not just a speed bump: **compute shaders**. WebGL was a rendering API that occasionally got abused for general-purpose computation through creative texture-encoding hacks. WebGPU treats GPU compute as a first-class citizen — you can run large parallel numeric workloads (physics simulation, image processing, machine-learning inference) without pretending your data is a texture and your algorithm is a fragment shader. This is the detail that matters most for where the platform is heading, and Section 6 comes back to it.

**Support status, and this is the headline of the whole chapter:** as of this year, WebGPU is enabled by default in stable releases across all four major engines. Chrome and Edge (and the rest of the Chromium family) have shipped it since Chrome 113. Firefox shipped it default-on for Windows, with Apple-Silicon macOS following, and Linux/Android support actively in progress through 2026 — check current status before you rely on it there specifically. Safari shipped it enabled by default starting with macOS Tahoe 26 and the matching iOS/iPadOS/visionOS 26 releases. That's the actual milestone underneath the "end of the WebGL era" headlines you may have seen: for the first time, every engine vendor has a shipped, default-on implementation, not a flag-gated experiment.

**What that doesn't mean:** universal *device* support. GPU driver quality varies wildly across the Windows and Android long tail, and "the browser supports WebGPU" is not the same claim as "this specific user's laptop will successfully create a WebGPU adapter." The correct production pattern is a fallback ladder — WebGPU first, WebGL2 as the safety net, Canvas 2D or a plain static image as the last resort for anything below that — and every serious engine (Three.js, Babylon.js) already automates this switch for you. Don't hand-roll it; use what the libraries give you.

## 4. WebXR: Where "Universal Support" Goes to Die

If WebGPU's story this year is convergence, WebXR's story is the opposite: a genuinely fragmented landscape that isn't converging on any visible timeline, and pretending otherwise will sink a project.

WebXR is the standard session API for VR and AR — it doesn't render anything itself, it hands your WebGL or WebGPU scene the head pose, controller data, and frame timing a headset or AR-capable device provides. It's the direct successor to the old **WebVR API**, which is fully deprecated and gone; if you find a tutorial still referencing `navigator.getVRDisplays()`, it's a decade stale.

Here's where things stand, platform by platform, without the marketing gloss:

- **Chromium on Android, plus the Meta Quest Browser:** full support, immersive-vr and immersive-ar, hand tracking, plane detection, passthrough. This is WebXR's home turf and it works about as well as the category gets.
- **Safari on visionOS:** immersive-vr sessions, enabled by default, with a distinctive gaze-and-pinch input model instead of handheld controllers. The **AR module is not implemented** — Apple's flagship spatial-computing device supports WebXR VR content but not WebXR AR content through the browser, a decision whose logic remains Apple's alone to explain.
- **Safari on macOS and iOS: no WebXR at all.** Not partial, not experimental-behind-a-flag — absent. This is the fact that sinks the most WebAR side projects: build a slick handheld AR demo, test it on an Android phone, ship the link, and every iPhone visitor gets a black screen or a polite unsupported-browser message.
- **Firefox: paused.** Desktop and Android support stalled after Mozilla wound down its dedicated Firefox Reality browser, and there's no public roadmap suggesting that changes soon.

Apple's actual answer for "let an iPhone user see something in 3D in their space" isn't WebXR at all — it's **AR Quick Look**: link to a `.usdz` model with `<a rel="ar" href="model.usdz">`, and Safari opens a native, first-party AR viewer with correct lighting and occlusion, one tap, zero JavaScript. It's not a platform you can build interaction logic inside of — it's a viewer — but for "see this product in your living room before you buy it," it's genuinely the best experience available on that device today, WebXR entirely bypassed.

The practical takeaway: if your audience is meaningfully iPhone-heavy and the use case is "view a 3D object in AR," reach for USDZ/AR Quick Look, not WebXR. If your audience is Android- or Quest-heavy and the use case is a full interactive immersive experience, WebXR is the right and only sane choice. Building one unified experience that serves both well, today, is not realistically possible — plan for two code paths, not a polyfill.

## 5. The Boring, Reliable Middle Ground: `<model-viewer>` and glTF

Not everyone needs a hand-rolled WebGL or WebGPU renderer. A huge fraction of "put a 3D object on a webpage" requests — furniture, sneakers, a product configurator — are fully served by **`<model-viewer>`**, a web component (built on Three.js under the hood) that wraps camera controls, lighting, and AR handoff into a single custom element:

```html
<model-viewer src="chair.glb" ar camera-controls auto-rotate></model-viewer>
```

One line, a rotatable, lit 3D object, and on supporting platforms a tap-to-AR button that routes to the right native mechanism per device (Scene Viewer on Android, Quick Look on iOS) without you writing platform-detection code yourself. The asset format underneath almost all of this is **glTF** (`.gltf`/`.glb`) — the de facto standard interchange format for web-delivered 3D, roughly playing the role for 3D assets that JPEG plays for photos: not the format artists work in, but the format everything gets compiled down to before it ships.

If a stakeholder asks for "can we show the product in 3D" and nobody's mentioned physics, multiplayer, or a game loop, this is very likely the entire correct answer. Reaching for raw WebGL when `<model-viewer>` would have shipped the same result in an afternoon is the 3D-graphics equivalent of hand-rolling a date picker.

## 6. Compute in the Browser: The Quiet Part That Matters Most Long-Term

WebGPU's compute-shader capability is the thread most coverage buries under gaming headlines, and it's arguably the more consequential one. General-purpose parallel computation — the same category of work that makes GPUs valuable for machine learning — is now reachable from a browser tab without a native app, a driver install, or a server round-trip. Client-side ML inference (running a model against a photo the user just took, entirely on their device, no upload), real-time physics for thousands of simultaneously simulated objects, and large-scale data-parallel image or signal processing all move from "needs native code" to "runs in a tab" territory as this matures. Pair it conceptually with **WebNN** (the Web Neural Network API, a higher-level, model-inference-focused sibling proposal aimed squarely at on-device AI) and the direction of travel is unambiguous: the browser is being handed real, general-purpose GPU compute, not just a fancier way to draw triangles. Expect this to be the quieter but more consequential half of "what WebGPU was actually for," once the rendering headlines settle down.

## 7. Use Cases, Honestly

**Product configurators and e-commerce.** Cars, furniture, sneakers, glasses — rotate it, change the color, view it in your room. `<model-viewer>` covers the simple version; a custom Three.js/Babylon.js scene covers the version with real-time material changes and lighting rigs.

**Browser-native games.** Babylon.js, Three.js, and PlayCanvas all target WebGL today with WebGPU as an increasingly production-ready renderer option, automatically falling back where it isn't available yet. Full AAA titles running natively in a tab remain a near-future story rather than a today story — the honest expectation among engine authors is professional 2D/motion tooling moving into the browser first, heavier 3D and AAA-scale work following over the next couple of years as WebGPU tooling and driver reliability mature further.

**Scientific and data visualization.** Point clouds, molecular structure viewers, GIS terrain rendering, medical imaging volumes — anywhere a dataset is inherently spatial and a flat chart (Chapters 1 and 2's territory) would flatten away the information that matters.

**Generative and creative 3D art.** The same crowd that adopted p5.js for 2D creative coding has a growing WebGPU-native equivalent forming, drawn by direct compute-shader access to build particle systems and procedural geometry that would have needed a native toolchain a few years ago.

**On-device AI inference.** Background removal, style transfer, object detection, and increasingly capable local language-model inference, running against WebGPU compute pipelines instead of a server API call — privacy-friendly by construction, since the data never leaves the device, and a use case that barely existed in the WebGL era.

---

## 8. Pros and Cons, Said Plainly

**What browser 3D gets you:** zero-install reach — a link works where a native app requires a store, a download, and a decision. WebGPU specifically gets you close to native-engine ergonomics (compute shaders, explicit pipelines) without leaving the browser sandbox.

**What it costs you:** real device and driver fragmentation that a fallback ladder mitigates but never fully erases, meaningfully higher battery and thermal cost than a well-optimized native app on the same hardware, and — WebXR being the sharpest example in this entire series — a platform landscape where "the API exists" and "your actual target device supports it" can be two completely different answers depending on which pocket the phone is in.

---

## 9. Where This Is Going

1. **WebGL doesn't disappear, it becomes the fallback tier.** The multi-year pattern to expect: new engine features target WebGPU first, WebGL keeps receiving maintenance and security fixes (see the SwiftShader removal) but stops being where anyone builds new capability.
2. **The Canvas/WebGPU convergence flagged in Chapter 1 is the same story from this chapter's side.** A single canvas switching between 2D and WebGPU contexts, WebGPU shaders usable as Canvas 2D filters — the wall between "2D canvas" and "3D canvas" that's existed since 2004 is being deliberately dismantled from both directions at once.
3. **WebXR's iPhone gap is the open question of this entire chapter**, and there's no public signal it resolves soon. Whether Apple eventually ships full WebXR AR on iOS, or keeps investing in Quick Look/USDZ as its permanent answer instead, is worth watching specifically if your business depends on reaching iPhone users in AR — right now, plan around Apple's actual answer, not the one you'd prefer they'd given.
4. **Compute-shader-driven, on-device AI is the sleeper thread.** Rendering triangles faster is a good story. A browser tab running real inference workloads without a server is the story that changes what kinds of applications get built as a tab instead of a native app at all.

---

## Closing the Series

Three chapters, one underlying pattern: every graphics technology on the web is a trade between how much the browser understands about what you're drawing and how fast it can draw it anyway. Canvas trades understanding for speed and is finally getting some of that understanding back through HTML-in-Canvas. SVG trades raw throughput for a browser that already knows what every shape means, and has for two decades. 3D spent twenty years standing on OpenGL's shoulders and is, this year, for the first time, standing on its own — with a compute story that has very little to do with graphics at all.

None of these technologies replace each other. A serious 2026 web application is entirely capable of using all three on the same page: SVG for the interactive chart, Canvas for the live sparkline redrawing sixty times a second next to it, WebGPU for the 3D product viewer below the fold. Knowing which one to reach for — and, as this series tried to make plain throughout, which one the browser is quietly doing enormous amounts of invisible work to make look effortless — is the actual skill. The APIs are just vocabulary.
