# Warp Deep-Dive: The Agentic Development Environment and Oz

**As-of date:** 16 June 2026
**Companion to:** `Landscape-2026-06.md`. That document mapped the paradigms (loops, state machines, delegation) and the workspace-analysis layer but missed Warp. This is the correction, written to the bone because Warp is now relevant on two of those axes at once: it ships a loop natively, and it is becoming a control plane for delegating across other agents.
**Lens:** CloudLib.EU. Commercial B2B SaaS, EU/DSGVO-bound, IP-sensitive, Node/Angular/Nx monorepo, small core team. The two questions that decide everything for us: what does it cost, and where does our code go.

> **Same freshness warning as the companion doc.** Versions, prices, and the exact boundary of what is self-hostable move in weeks. The licensing, the architecture, and the data-flow shape age more slowly. Re-verify anything load-bearing against the sources at the bottom before you act on it.

## 0. Verdict first (the problem before the praise)

**The problem, stated plainly:** Warp open-sourced its *client*, not its *brain*. The terminal is AGPL-3.0 and auditable. The parts that hold the value, the Oz cloud orchestration platform and the AI inference path, are proprietary and route through a US-hosted proxy. For an IP-sensitive, DSGVO-bound EU SaaS, the *default* configuration (Free or Build plan) is a US-cloud dependency where the agentic features are exactly the ones that transmit your terminal content, and on the Free plan telemetry is *mandatory* to use AI at all. That is a **NO** for sensitive CloudLib work as shipped.

**What is genuinely good, and why this is not a dismissal:** the terminal UX is the best in the category, Agent Mode is a real autonomous loop you do not have to build, and Oz is the cleanest *multi-harness control plane* anyone has shipped. It does not compete with Claude Code so much as orchestrate it. If you ever run a fleet of agents and need governance and audit across harnesses, Warp is the most credible answer, and an Enterprise configuration (self-hosted Oz on Kubernetes, BYOK, Zero Data Retention) is a plausible path to a DSGVO-acceptable posture.

**The one-line read:** Warp's value is orchestration and UX, not sovereignty. For pure DSGVO-safe autonomous loops, the companion doc's OpenCode air-gapped pick is still cleaner. For orchestrating a mixed fleet of Claude Code / Codex / Warp agents with governance, Warp is unmatched, at the cost of a US-vendor cloud dependency you have to engineer your way out of.

**Three things that matter most, up front:**

1. **Licensing is a non-issue for using it, a real thing if you embed it.** AGPL-3.0 on the client does *not* infect CloudLib's code when you merely use Warp as your terminal. It only bites if you fork, modify, or redistribute Warp, or run a modified Warp as a network service. Details in Section 5.
2. **The data flow is the real flag, not the licence.** US-hosted AI proxy, account required, ZDR gated to Business/Enterprise, telemetry mandatory for AI on Free. Section 7.
3. **Oz is the actual story.** Not "another coding agent." A control plane that runs Claude Code, Codex, and Warp Agent side by side. Section 3. This is the concrete instance of the companion doc's thesis: the harness is interchangeable, you sit at the control plane.

## 1. What Warp actually is now (the identity shift matters)

Warp launched in 2021 as a reimagined terminal: Rust, GPU-accelerated, a "Blocks" model that groups each command with its output, and modern editing. AI arrived incrementally: natural-language-to-shell, then a chat panel, then "Agent Mode," one of the first command-line agents with direct terminal access to run commands and read files.

The identity changed in April 2026. Two moves, close together:

- **Warp 2.0, the "Agentic Development Environment" (ADE), around 7 April 2026.** Warp stopped calling itself a terminal. The pitch became: replace the terminal + IDE + chat trio with one agent-native surface.
- **Open-sourcing the client, 28 April 2026.** Warp put its Rust client on GitHub (`warpdotdev/warp`, ~42k stars, 98% Rust) under AGPL-3.0, with OpenAI as founding sponsor and GPT models (including GPT-5.5) powering the agentic workflows that now ship improvements to Warp itself. Public GitHub issues became the system of record for the roadmap. They call the model "Open Agentic Development."

Mentally, separate Warp into three layers, because they have different licences and different privacy implications and people conflate them constantly:

| Layer | What it is | Open or proprietary | Where it runs |
|---|---|---|---|
| **The client** | The Rust terminal/ADE you install | Open source (AGPL-3.0; UI crates MIT) | Your machine |
| **Warp Agent runtime** | The agent that plans, edits, runs commands, self-corrects (same engine as "Agent Mode") | Proprietary | Local execution, but AI inference goes through Warp's US-hosted proxy |
| **Oz** | Cloud platform that runs and orchestrates agents (including Claude Code and Codex) at scale | Proprietary (self-hostable on Enterprise) | Warp cloud, or your Kubernetes, or both |

"Warp is open source" means "Warp's client is open source." It does not mean the agentic platform is open, and it does not give you an exit from the cloud by itself. Hold that distinction; the rest of the document depends on it.

## 2. The loop story

Warp offers loops natively. Concretely, there are two levels of loop, and they map onto the companion doc's spectrum.

**Level 1, the in-terminal autonomous loop: Agent Mode.** Agent Mode (the same runtime as "Warp Agent") takes a natural-language goal, makes a multi-step plan, runs commands, reads their output, edits code, runs tests, corrects itself on failure, and reports progress, without you driving each step. This is the classic agent loop (plan, act, observe, decide, repeat) shipped as a product feature with native terminal access. In the companion doc's terms, this is "a loop you do not have to build." It is closer to the managed end than to Ralph: it runs as a continuing process with managed context, not as a fresh-context-per-iteration bash loop. Different philosophy from Ralph (Section 8), same family.

**Level 2, the orchestration loops: Oz.** On top of Agent Mode, Oz adds the loop patterns that make this interesting for automation:

- **Scheduled loops (cron).** Oz agents run on a schedule. The literal command is `oz schedule --skill "flag-cleanup" --cron "0 2 * * *"`, or you set it in the web app. This is the "agent that wakes up and does a job repeatedly" loop, native, no scaffolding.
- **Automatic multi-agent orchestration loops.** Oz can spin up and coordinate multiple subagents in parallel for long-horizon tasks (feature builds, code migrations, deployments), with auto-tracking and steering, without you wiring the coordination by hand.
- **Triggered loops.** Runs can fire from the terminal, or from Slack, Linear, and GitHub integrations, or via API/SDK. So "PR opens, agent runs" style loops are first-class.

**The controlled-autonomy part is built in, which the companion doc argued is mandatory.** Warp's stance is humans-in-the-loop by default, with granular, configurable permissions: whether agents auto-accept diffs, whether they can read files without asking, whether they can run commands autonomously, an allowlist and denylist of commands, and which MCP servers are usable without prompting. You can dial any single task up to full autonomy or keep approvals. This is the "cap it and gate it" discipline the companion doc insisted on, shipped as settings rather than something you bolt on.

So: yes, loops out of the box, at both the single-agent and the fleet level, with permission gates included.

## 3. Oz: the multi-harness control plane (this is the real differentiator)

This is the part that makes Warp matter beyond "nice terminal," and the part the companion doc's framework predicted. Oz launched in February 2026 as a cloud platform for running and orchestrating coding agents at scale (sandboxing, scheduling, monitoring, governance), so you stop building agent scaffolding yourself. The May 2026 upgrade is what makes it strategically interesting:

**Oz is the first control plane that runs Claude Code, Codex, and Warp Agent side by side.** One dashboard, consistent access controls, governance policies, and audit logs across all three harnesses. You can compare how each performs and assign the right one per task. Multi-harness orchestration is in beta and available to all users. The explicit framing from Warp: companies should not have to bet their future on a single model or harness.

That is the companion doc's thesis made concrete: **the harness is becoming interchangeable, and the durable seat is the orchestration and governance layer.** Warp is betting the company on exactly that.

Mechanics worth knowing:

- **Cross-harness parent/child.** A Warp Agent parent run analyzes a task, splits it, and dispatches subagents: for example, Claude Code subagents for code-review-heavy steps and Codex subagents for high-volume edits, then coordinates the outputs. Important asymmetry: only Warp Agent can be the *parent*; Claude Code and Codex can be children but not orchestrators. Warp Agent is Oz's default harness.
- **Cross-harness Agent Memory (research preview).** A long-term memory store indexed over your organizational knowledge, with pluggable sources (files and skills, MCP servers, databases, enterprise apps), so any agent on any harness can pull the right context. The memory store is owned by the organization deploying it; Warp can host it or you can run your own. This is the only cross-harness memory system shipping.
- **Skills as agents.** Any Skill (including Claude Code or Codex skills, or anything in a `.agents/` directory) is launchable as a cloud agent: `oz agent run-cloud --skill <slug> --environment <slug>`. Skills are portable across harnesses here.
- **Auto-tracking and control surfaces.** Every Oz agent produces a link and an audit trail and is controllable via CLI and API. Local parallel sessions (separate tabs/panes), isolated git worktrees per agent, and Oz cloud fan-out (`/orchestrate`, `/plan`, the Oz CLI/web/API) are the three coordination modes.
- **Self-hosting.** Oz can run on Warp's infrastructure, on your own (Kubernetes pods, with or without Docker, fitting into existing remote dev environments), or a mix. Per-team billing, individual credit caps, and per-agent scoped permissions are part of the release. (Caveat on how complete self-hosting is, in Section 7.)

The practical read for CloudLib: if you stay on one harness (Claude Code), Oz is overhead you do not need yet. The moment you are running a *fleet* across harnesses and need audit, governance, and a single pane of glass, Oz is the most credible option in the market. That is a "later, maybe" not a "now."

## 4. Architecture and platforms

- **Client:** Rust (98% of the repo), GPU-accelerated rendering, the Blocks model (command + output as a unit), descended from terminal internals (Alacritty, NuShell, Tokio, Fig completion specs in the dependency tree).
- **Context file:** `WARP.md` at the repo root is Warp's project-context convention, its equivalent of `CLAUDE.md`. Warp also reads `AGENTS.md` (the cross-tool standard from the companion doc), and the repo carries `.agents/skills`, `.claude`, a `specs/` directory, and `.mcp.json`, so it speaks the now-standard context dialects.
- **Local codebase indexing:** the client indexes your codebase locally, honoring a `.warpindexingignore` file. This is the workspace-analysis layer (companion doc Section 3) handled in-client.
- **MCP:** full Model Context Protocol support; team-shared MCP server libraries on the Build tier and up.
- **Model routing and BYOK:** Warp Agent routes across a model catalog, and you can bring your own key for OpenAI, Anthropic, or Google, which routes AI through your own provider account for visibility and billing. (BYOK does not fully remove Warp from the data path; Section 7.)
- **Platforms:** macOS, Linux, and Windows. Linux ships as `.deb`, `.rpm`, `.tar.zst`, and AppImage for both x64 and ARM64. (It began Mac-only; the cross-platform support is real now.)

## 5. Licensing (precise, because you are licence-sensitive)

Confirmed directly from the repository, not an aggregator:

- **The client is dual-described:** the UI framework crates (`warpui_core` and `warpui`) are **MIT**; **the rest of the repository is AGPL-3.0**.
- **Oz, Warp AI, and Warp Drive are proprietary.** Open-sourcing the client did not open these. Oz is self-hostable on Enterprise but it is not open source.

**What AGPL-3.0 means for CloudLib, stated carefully so you neither panic nor get false comfort:**

- **Using Warp to build CloudLib does not affect CloudLib's licensing at all.** You are a *user* of the tool. Code you write in the terminal is yours. AGPL's copyleft and its network clause bind whoever *conveys* (distributes) the program or runs a *modified* version as a network-accessible service. Editing your own files with an AGPL editor triggers nothing. This is the common AGPL misconception; the correct answer is that normal use is fine.
- **AGPL bites only if you do one of these:** fork or modify Warp and distribute it; or run a modified Warp as a service that users interact with over a network (then you must offer your modified source under AGPL, including to those network users). CloudLib will do neither, so this is not a practical constraint for you.
- **The MIT carve-out** lets you reuse the UI framework crates permissively in unrelated projects, if you ever wanted to. The valuable agentic/cloud code is not in that carve-out, and is not open anyway.
- **Contributing code upstream** would be under AGPL. I did not verify whether a contributor licence agreement applies; check `CONTRIBUTING.md` before contributing if that matters to you.

Net: the licence is a green light for *use*. The thing to scrutinize is not the licence, it is where your data goes, which is the next section.

## 6. Pricing (you are paying for AI compute, not the terminal)

Figures vary across low-quality aggregator sites; the numbers below come from Warp's own docs, detailed reviews, and the Hacker News discussion. Verify current terms before committing, because Warp has changed this model more than once and it drew complaints each time.

| Plan | Price | Credits / limits | Notes |
|---|---|---|---|
| **Free** | $0 | ~150 AI credits/mo for the first two months, then ~75/mo | **Telemetry must be ON to use AI features on Free.** Secret Redaction, Network Log, SOC 2 included. |
| **Build** | $20/mo | ~1,500 credits/mo (community reports: do *not* roll over) | BYOK (OpenAI/Anthropic/Google), cheaper prepaid "Reload Credits," team MCP libraries. |
| **Max** | higher than Build | Higher monthly credit allowance, better effective credit rate | For heavier AI usage. |
| **Business** | $50/user/mo | Shared credits, up to 50 members | SSO/SAML, admin controls, **Zero Data Retention by default**, telemetry off by default. |
| **Enterprise** | Custom | Custom | BYO LLM, self-hosted Oz, dedicated account manager, ZDR, advanced controls on request. |

**The honest framing from the community: "you are really paying for AI compute, not the terminal."** The terminal is free; the credits are the product, and the AI-compute market is a price war, so this is the volatile axis.

**The catch worth flagging explicitly (it is exactly the kind of hidden fee/condition to watch):** from **1 July 2026**, on Business and Enterprise, *local* agent runs that use customer-supplied inference (BYOK, a custom inference endpoint, or BYOLLM) begin consuming **platform credits**. Warp's reasoning: even when it is not paying for the model call, its platform infrastructure is still running the agent. Translation: bringing your own key does not make you free of Warp's metering on the higher tiers once the preview ends. Local runs on Free/Build/Max, and local runs on Business/Enterprise using Warp-managed inference, do not consume platform credits. Budget for this if you plan a BYOK + Business setup.

## 7. Data, privacy, sovereignty (the section that decides it for CloudLib)

This is where an IP-sensitive DSGVO product lives or dies, so it gets the most detail and the most caution.

**Account required.** Unlike a classic terminal, Warp requires a login. Warp frames this as normal for a cloud app like Figma or GitHub. For your threat model, it means there is an identity and an account-level data relationship by design.

**Warp AI data flows through a proxy to US-hosted APIs.** This is the core sovereignty fact, from Warp's own security page. Your terminal context and prompts, when AI features are active, leave your machine and transit Warp's US-hosted infrastructure on the way to the model providers. US hosting means CLOUD Act exposure regardless of the contractual promises layered on top.

**The agentic features are the ones that transmit.** Code and files stay on your machine *unless* you use features that send them, and the features that send them are precisely Agent Mode, Active AI, Cloud History, and Block Sharing. In other words, the moment you use the thing you installed Warp for (the agent), terminal content goes to the proxy. You can disable those features, but then you have a terminal, not an ADE.

**Telemetry and the Free-plan catch.** Telemetry (Sentry for crash reporting, Rudderstack for analytics) is opt-out via Settings > Privacy, and a built-in **Network Log** lets you audit every event and network request in real time, which is a genuine transparency feature. **But on the Free plan, telemetry must be enabled to use AI features at all.** Paid plans can opt out of telemetry and keep AI. So "free" and "private" are mutually exclusive here.

**Secret Redaction** is applied to AI interactions (Warp says unconditionally, and lists it as available even on Free) to strip sensitive values before they leave. A critical third-party assessment argues the *full* control set you would want is effectively gated to paid tiers; treat the unconditional-redaction claim as Warp's position and verify the org-wide enforcement controls you specifically need.

**Zero Data Retention is gated.** ZDR (no AI-interaction or console data collected, none used for training) is covered on **Business and Enterprise** plans and is the default there, with data collection off by default on those tiers. It is **not** in force on Free or Build. And the sharper point: Warp's relationship with the *model providers* is ZDR (Anthropic, OpenAI, etc. do not retain or train on your data), but on non-ZDR plans **Warp itself reserves the right to use collected data to train models and improve Warp**. So on Free/Build, "the model provider will not train on it" is true while "Warp might use it" is also true. Read both sentences together.

**Compliance posture.** SOC 2 Type 2, with claimed adherence to GDPR, CCPA, and the UK Data Protection Act, and a published subprocessors list. For DSGVO specifically, "adheres to GDPR" by a US company doing US-hosted processing is not the end of the analysis; the EU-to-US transfer mechanism (SCCs, the EU-US Data Privacy Framework status) and a Data Processing Agreement are what actually matter, and those need confirming with Warp directly, not inferring from a marketing line. This is not legal advice; involve counsel.

**Self-hosting Oz: improvement, with an asterisk.** Warp now offers Oz self-hosting (Kubernetes, with or without Docker), and Anthropic's own customer page on Warp confirms customers can self-host the platform, run it on Warp's infrastructure, or mix both. That materially improves the sovereignty story versus the old fully-SaaS model: agent *execution* can run in your own cluster. The asterisk: a recent critical assessment claims the core cloud is not truly self-hostable, and the parts most likely to remain Warp-cloud-bound are the AI inference proxy and the account/auth/control-plane services. The honest position is that self-hosting covers the orchestration runtime, but the default AI inference path is still US-hosted unless you combine it with BYOK or a custom inference endpoint, and the exact boundary of "what stays in Warp's cloud" needs direct confirmation from Warp before you rely on it for DSGVO.

**DSGVO verdict for CloudLib:**

- **Free or Build, as shipped: not acceptable for sensitive code.** US-cloud data flow for the agentic features, telemetry mandatory for AI on Free, Warp may use your data on non-ZDR plans.
- **A defensible posture exists but you have to build it:** Enterprise (or at least Business) + ZDR + BYOK or custom EU-region inference endpoint + self-hosted Oz on your own Kubernetes. That gets most of the data into your control. It is a stitched-together Enterprise configuration, not the default, it still involves a US vendor and account, and it costs more. Worth it only if Oz's multi-harness governance is something you actually need.

## 8. Where Warp sits versus the companion doc's framework

Warp is unusual because it is **both a harness and a control plane**, which is why it did not fit cleanly into the original tool table.

| Comparison | How Warp relates |
|---|---|
| **vs Claude Code** | Not either/or. Claude Code is a harness that Warp's Oz *runs and orchestrates*. Warp adds the terminal UX, permission gates, and cross-harness governance. You can drive Claude Code *through* Warp. If you love Claude Code's output quality, Oz lets you keep it while gaining orchestration. |
| **vs OpenCode (the companion doc's air-gapped pick)** | Opposite sovereignty posture. OpenCode air-gapped is local-first, zero-egress, the sovereignty choice. Warp is US-cloud-first with sovereignty available only via an Enterprise build-out. For pure DSGVO sovereignty, OpenCode wins; for multi-harness orchestration plus governance plus UX, Warp wins. They can coexist: OpenCode is even listed as a harness you can run in Warp tabs. |
| **vs Cursor / Antigravity / Devin Desktop** | Those are IDE-centric surfaces. Warp is terminal-centric plus a control plane. Different shape of tool. |
| **vs Ralph (companion doc Section 2a)** | Warp Agent is a managed, in-session loop, not Ralph's deliberately-dumb fresh-context-per-iteration bash loop. If you want Ralph's anti-context-rot guarantee, Warp is not it; if you want a polished managed loop with gates, Warp is. |
| **vs LangGraph / Temporal (Section 2b)** | Oz is a managed *operational* control plane (scheduling, sandboxing, audit, governance), not a code-level state-machine framework. Different layer. You would still reach for LangGraph/Temporal to build an agent *inside* a product; you would reach for Oz to *operate* a fleet of coding agents. |

**The unique slot Warp occupies:** a multi-harness control plane with audit, governance, scheduling, and a shared memory layer, fronted by the best terminal UX in the category. Nobody else does exactly this combination as cleanly right now. That is the reason to track it even if you do not adopt it.

## 9. Honest assessment for CloudLib (problem first, then the call)

**The problem, restated so it is not buried:** the default Warp configuration is a US-cloud dependency where the agentic features transmit your terminal content, the account is mandatory, ZDR is paywalled, and BYOK still gets metered on the tiers where it is available. For an IP-sensitive DSGVO B2B SaaS, that rules out Free/Build for sensitive work.

**What is genuinely strong:** the terminal UX is excellent and would be a daily-driver upgrade over a classic terminal; Agent Mode is a real loop out of the box with permission gates; Oz's multi-harness governance is unique and is the right tool *if and when* you run a fleet; and the self-host + BYOK + ZDR path is a credible route to acceptability.

**The call:**

- **Do not make Warp your default agent for sensitive CloudLib code on Free/Build.** The data flow is the disqualifier, not the licence.
- **It is fine as a local terminal plus Agent Mode for non-sensitive or experimental work**, on a paid plan with telemetry off, where nothing proprietary is in play. Even there, assume terminal content reaches the US proxy when the agent is active.
- **Evaluate Oz Enterprise seriously only if you scale to a multi-harness fleet** and need governance and audit, with self-hosted Oz on your own Kubernetes, BYOK or an EU-region custom inference endpoint, and ZDR. A small team is probably not there yet. This is a "when you have five agents running and need a control plane" decision, not a "this quarter" one.
- **For DSGVO-safe autonomous loops specifically, the companion doc's OpenCode air-gapped pick remains the cleaner choice.** Warp's value is orchestration and UX, not sovereignty. Do not adopt Warp expecting sovereignty out of the box; you would be disappointed and exposed.

**The strategic read:** Warp is the clearest product-level bet on the companion doc's central thesis, that the harness and model are interchangeable and the durable seat is the orchestration/governance layer. Even if you do not run it, that bet is worth understanding, because if it is right, the thing to invest in is your portable context and your control plane, not any single agent. Warp is what "control plane" looks like when someone builds it for real.

## 10. Open questions to resolve before any serious adoption

- **The exact self-hosting boundary.** Does AI inference and account/auth stay in Warp's US cloud even when Oz execution is self-hosted? This is the single most important unknown for DSGVO. Get it in writing from Warp.
- **EU data residency for the AI proxy.** Is there an EU-region option, or is a custom EU inference endpoint the only way to keep inference in-region?
- **Transfer mechanism and DPA.** SCCs, EU-US Data Privacy Framework certification status, and a signed Data Processing Agreement. Counsel question.
- **Platform-credit economics after 1 July 2026** for a BYOK + Business setup. Model the real cost, not the sticker price.
- **Contributor licence agreement.** Whether contributing to the open-source client involves a CLA (unverified here).
- **Credit roll-over.** Confirm current behavior; community reports say Build credits do not roll over, and Warp's own model has changed before.
